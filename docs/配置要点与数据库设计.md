# 配置要点与数据库设计

## 目标边界

本数据库是“固件驱动的只读运营商配置目录”。iOS/Android/baseband 版本变化时重新提取并发布一个新 SQLite 文件。使用它的 IMS 客户端自行管理 SIM、线路、注册会话和运行日志。

数据库不承担：

- per-line profile 绑定和用户 override；
- SIM 身份、IMEI 或 ISIM 文件实际内容；
- AKA challenge/response 和 IPsec/SIP 会话密钥；
- 注册尝试、状态、统计或客户端 fallback 日志。

因此参考建议稿中的 `line_ims_binding`、`sim_identity`、`registration_attempt` 不进入本仓库 schema。需要它们的业务项目可以在自己的数据库里用 `profile_id` 外部关联本 catalog。

## 为什么只保留一个 schema

LTE、5G 和 VoWiFi 的 IMS 注册共享 home domain、realm、身份来源、IMS AKA 和 SIP REGISTER 规则。平台与接入方式的差异主要发生在静态配置的来源以及 bearer/P-CSCF 获取方式。

```text
iOS Carrier Bundle ─┐
Android CarrierConfig ├─> carrier profile ─┬─ LTE/EPC access
Modem MCFG/CSC ─────┘                     ├─ NR/5GC access
                                          ├─ Wi-Fi/ePDG access
                                          └─ shared IMS/SIP config
```

所以 iOS 和 Android 只拥有适配器目录，不拥有独立表结构。

## 已确定的数据源路线

实现顺序已经确定为：Pixel 官方 Factory Image/完整 OTA、iOS 官方 IPSW Carrier Bundle、Samsung 官方 AP/CSC/IMSService、独立 modem 适配器。三方 ROM 不作为主要权威来源。详细工具选择和里程碑见 [`提取器路线图.md`](./提取器路线图.md)。

这个顺序只决定工程实施优先级，不决定跨平台字段的绝对可信度。iOS Carrier Bundle、Android framework 配置和 modem provisioning 可能描述同一运营商的不同设备范围或不同配置层，合并前必须比较设备、OS/build、baseband 和匹配条件。

## Schema 分区

| 分区 | 表 | 内容 |
|---|---|---|
| 发布 | `catalog_release`、`schema_metadata` | release id、生成器版本、sealed 状态 |
| 来源 | `source_snapshots`、`profile_sources`、`field_evidence` | 固件/基带版本、路径、解析器、字段证据 |
| 运营商 | `carriers`、`carrier_aliases`、`plmns` | 名称、国家、MCC/MNC、TADIG |
| 图标 | `visual_assets` | 图片 BLOB、本地/远端来源、哈希、许可、官方标记 |
| 配置匹配 | `carrier_profiles`、`profile_match_rules` | PLMN、公开 IMSI/ICCID prefix、GID、SPN、设备范围 |
| 接入 | `access_configs`、`pcscf_discovery_methods`、`dns_resolvers` | LTE、5G、ePDG、N3IWF 的 APN/DNN 与发现规则 |
| 端点 | `network_endpoints` | ePDG、N3IWF、P-CSCF、registrar、BSF、E911 |
| IKE | `ike_configs`、`ike_identity_rules`、`crypto_proposals` | EAP、IDi/IDr、端口、生命周期、NAT-T、DPD 和有序 proposal |
| IMS 身份 | `ims_configs`、`ims_identity_templates` | IMPI、IMPU、Contact identity 的来源与模板，不含用户实值 |
| IMS/SIP | `sip_register_configs`、`sip_header_rules`、`sip_contact_parameters`、`sip_security_mechanisms`、`sip_status_policies` | 公共及 LTE/5G/VoWiFi 覆盖、REGISTER、Header、安全和状态策略 |
| 服务 | `service_capabilities`、`entitlement_configs`、`emergency_configs` | VoLTE、VoNR、VoWiFi、SMS、授权和紧急能力 |
| 扩展 | `raw_config_values` | 经过白名单过滤、尚未归一化的公共静态键 |

旧设计中的 profile revision/draft/active 被删除。历史通过保留旧 release 文件表达，避免把“编辑配置”和“固件事实”混为一谈。

## 注册配置继承

每个运营商可以有一条 `scope='common'` 的公共 REGISTER 配置，并为 `lte_epc`、`nr_5gc`、`wifi_epdg` 分别建立 `scope='access'` 的覆盖配置。

```text
客户端协议默认
  └── common REGISTER
        ├── LTE override
        ├── NR override
        └── VoWiFi override
```

接入覆盖中的 `NULL` 继承父配置；父配置仍为 `NULL` 时才使用客户端协议默认。Header 和 Contact 列表使用独立规则：没有子表记录表示继承，`action='omit'` 表示明确不发送，禁止用空字符串表示删除。

`v_sip_register_catalog` 已合并公共和接入专用的标量字段。Header、Contact 和 Security-Client 是有序多值，消费者按 `parent_register_config_id` 和 `inherit_parent_headers` 合并对应子表。

未提取到的字段保持 `NULL` 或不创建对应子表记录。这表示“来源未声明”，不表示关闭、空字符串或已验证的客户端默认。只有来源明确关闭时才写 `0`，只有来源明确要求省略某个 SIP 字段时才写 `action='omit'`。

## 身份模板

`ims_identity_templates` 保存 IMPI/IMPU 的**来源和格式**，例如在 ISIM 缺失时使用：

```text
{imsi}@ims.mnc{mnc3}.mcc{mcc}.3gppnetwork.org
sip:{imsi}@ims.mnc{mnc3}.mcc{mcc}.3gppnetwork.org
```

`ike_identity_rules` 保存 IKE_AUTH 的 IDi/IDr 类型、模板和发送策略，例如 IMSI NAI 或 ePDG FQDN。实际 IMSI、网络 pseudonym 和 fast-reauth identity 只在运行时内存中存在。

## 4G/LTE IMS

数据库需要表达：

- IMS APN、IP family、漫游协议和是否 always-on；
- P-CSCF 的有序发现方式，LTE 通常优先 PCO；
- IMS domain/realm、ISIM 或按 IMSI 派生的身份来源；
- IMS AKA、SIP transport、IPsec-3GPP sec-agree；
- REGISTER Expires、Contact feature tags、PANI、P-Visited-Network-ID 和状态码策略；
- VoLTE、SMS over IMS、MMTel、UT/XCAP 和 emergency 能力。

QCI、实际 bearer、分配地址和动态 P-CSCF 属于网络运行时结果，只有固件明确静态声明的要求才进入 catalog。

`access_configs` 还可保存固件公开提供的 APN 认证类型、静态用户名/密码和 MTU。这里的静态 APN 凭据是所有该运营商设备共享的 provisioning 值，不是 SIM/用户密码；提取器仍必须通过来源路径证明其来自公开固件配置。

## 5G IMS

5G SA 增加：

- IMS DNN；
- PDU session 地址族；
- 可选 S-NSSAI（SST/SD）和 SSC mode；
- EPCO 等 P-CSCF 发现；
- VoNR、EPS fallback 和紧急 PDU session 能力。

完成 5G PDU session 后仍然使用共享 IMS/SIP 配置。5G NSA 往往仍锚定 EPC，不应只因无线侧显示 NR 就套用 `nr_5gc`。

## VoWiFi

传统 VoWiFi 的静态配置包括：

- ePDG FQDN、标准 PLMN 派生或明确 override；
- IKE 500 与 NAT-T 4500 两个端口；
- IPv4/IPv6、DNS 来源、内部地址和 P-CSCF CFG 请求；
- EAP-AKA/EAP-AKA'、IDi/IDr、证书校验；
- IKE SA/Child SA proposal、NAT keepalive、DPD、reauth、MOBIKE、fragmentation；
- tunnel 建立后共享的 IMS/SIP REGISTER 配置。

5GS untrusted non-3GPP access 的 N3IWF 不是简单替换 ePDG 域名，因此 schema 使用独立的 `wifi_n3iwf` access kind。

## 对提供的 YAML 的处理

| YAML 字段 | 处理 |
|---|---|
| MCC/MNC、`id` | `plmns`、`carrier_profiles`、`profile_match_rules` |
| ePDG、APN、IP stack | `access_configs`、`network_endpoints` |
| DNS fallback | `dns_resolvers.position` |
| IKE/ESP proposals | `crypto_proposals.position` |
| IMS domain/realm/transport | `ims_configs` |
| REGISTER scalar policy | `sip_register_configs`，公共配置加 access override |
| Supported/Require 等 Header | `sip_header_rules`，支持 add/replace/omit 与报文阶段 |
| Contact 参数 | `sip_contact_parameters` |
| Security-Client | `sip_security_mechanisms`，SPI/端口仍由运行时填写 |
| 状态码策略 | `sip_status_policies` |
| E911/entitlement | `emergency_configs`、`entitlement_configs` |
| `device_identity_imei` | 禁止入库 |
| `access_type: wlan1` | 禁止入库；这是运行时网卡名，不是 IMS access type |
| `algorithm_policy`、AKA workaround | 只有固件明确声明为运营商要求时才入库，否则属于使用方客户端策略 |

`expires: 600000` 必须先确认单位；schema 只接受明确的 `requested_expires_seconds`。空 `ims_pcscf` 不写成空字符串，而是没有 static endpoint，并记录其他发现方式。

## 图标设计

NekokoLPA1/2 提供了两个有价值的参考点：

1. 按 MCC/MNC、GID、profile/provider name 解析不同运营商或 MVNO 图标。
2. operator icon 与国家旗帜是不同资产，不能混用。

本项目的差异是下载发生在数据库封存之前：

- `icons/package_icons.py` 以 shallow + sparse 方式更新 `icons/vendor/NekokoLPA2`，只保留 `operator_icon_source.dart` 和 `LICENSE`，并从当前代码读取 operator-icons 服务地址。
- 打包器只根据最终数据库已有的 PLMN、GID、SPN 和 profile name 下载所需 PNG，不镜像整个上游目录。
- `visual_assets.asset_data` 保存原始二进制 BLOB，不使用 base64；同时保存远端来源、SHA-256、尺寸、media type、许可和 attribution。
- `carriers.primary_asset_id` 提供默认图标，`carrier_profiles.profile_asset_id` 可覆盖 MVNO/配置变体。
- `v_carrier_catalog` 只返回轻量 `asset_id`，消费者按需从 `v_visual_asset_catalog` 读取 BLOB，避免普通配置查询反复搬运图片。
- operator-icons 的统一再分发许可无法确认，打包记录使用 `NOASSERTION`；项目自制 fallback badge 继续用于无需上游 logo 的发布场景。
- 上游 TOML 只在构建内存中解析，数据库只记录其 URL 和 SHA-256，不复制可能类似 ICCID 的 profile name。

## 只读保证

SQLite schema 本身不能阻止拥有文件写权限的进程重新打开数据库并修改。实际保证由发布流程提供：

1. `tools/init_db.py` 拒绝覆盖已有文件。
2. 导入器只构建新 release。
3. `tools/seal_db.py` 先更新 NekokoLPA2、匹配并嵌入图标，再完成外键/quick check、设置 sealed 并清除文件写位。
4. 消费者使用 `mode=ro&immutable=1`。
5. 发布新版本时原子替换文件或符号链接，旧 release 保持不变。

## 来源冲突和证据等级

来源合并遵循以下规则：

1. 官方固件/配置包中可定位到原始键的值使用 `evidence_kind='extracted'`。
2. 按 3GPP 标准生成的域名或身份格式使用 `evidence_kind='standard_derived'`。
3. 第三方 ROM 默认只作辅助证据，不能静默覆盖同设备/版本的官方固件值。
4. 同字段冲突时通过 `field_evidence` 保留候选值和置信度；设备范围不同则拆分 `carrier_profiles`。
5. framework 能力开关、厂商 IMS 行为和 modem provisioning 分层记录，不能因为名称相近就视为同一个事实。
6. 反编译或逆向后语义未确认的键只允许进入白名单化的 `raw_config_values`。

## 外部查询

```sql
SELECT * FROM v_carrier_catalog WHERE plmn = '310260';

SELECT a.media_type, a.asset_data
FROM v_carrier_catalog AS c
JOIN v_visual_asset_catalog AS a USING (asset_id)
WHERE c.plmn = '310260';

SELECT *
FROM v_access_catalog
WHERE profile_id = ?
ORDER BY CASE access_kind
  WHEN 'nr_5gc' THEN 1
  WHEN 'lte_epc' THEN 2
  WHEN 'wifi_epdg' THEN 3
  ELSE 4
END;

SELECT *
FROM v_endpoint_catalog
WHERE profile_id = ?
ORDER BY service, position;
```
