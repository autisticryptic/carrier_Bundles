# iOS/Android 提取器路线图

## 结论

首版按以下顺序实现：

1. Android Pixel 官方 Factory Image/完整 OTA。
2. iOS 官方 IPSW 中的 Carrier Bundle 和 Country Bundle。
3. Samsung 官方固件的 AP、CSC/OMC 和 IMSService。
4. Qualcomm MCFG/MBN 等独立 modem 适配器。
5. 三方 ROM 只作为差异检查和缺失字段的辅助证据。

这个顺序优先保证来源可重复获取、版本和设备可定位、提取过程可自动化。它不表示 Pixel 的运营商配置比 Samsung 更完整，也不表示 iOS 的 IMS 配置全部位于 baseband 固件中。

## 数据源边界

“ROM/固件中的运营商配置”至少分为三层，提取器不能把它们混为一个完整 profile：

| 层次 | 典型内容 | 能否作为静态 catalog 数据 |
|---|---|---|
| 系统/框架 | CarrierConfig、APN、resource overlay、Carrier Bundle plist | 可以，保留来源路径和适用版本 |
| 厂商/IMS 实现 | vendor 配置、IMSService、ePDG 配置、`cfg.db` | 可以，但字段含义需要解析器证据 |
| modem/SIM/网络运行时 | MCFG、NV、ISIM、AKA、动态 P-CSCF、分配地址 | 只收录公开固件内的静态规则；禁止收录用户值和运行时结果 |

从刷机包提取到的通常是注册所需的**静态候选配置**，不是可直接完成注册的用户凭据。IMSI、ICCID、IMPI/IMPU 实值和 AKA 密钥来自用户 SIM/ISIM，必须由使用方在运行时提供，不能写入本数据库。

## 阶段一：Pixel 官方固件

Pixel 是首个 Android 目标，原因是官方 Factory Image 和完整 OTA 具有清晰的设备、版本和构建号映射，适合构建可重复的下载、解包、扫描和回归测试流水线。

首版提取范围：

- Factory Image/完整 OTA 的 URL、设备代号、系统版本、build id、baseband 版本和 SHA-256。
- `product`、`system`、`system_ext`、`vendor` 等镜像内的 CarrierSettings、CarrierConfig、APN、overlay 和 vendor carrier 配置。
- 可识别的 IMS APN/DNN、P-CSCF 发现、IMS/ePDG 能力、静态端点和匹配规则。
- 每个规范字段对应的原始文件、键路径、解析器版本和置信度。

建议工具和参考：

- [Google Pixel Factory Images](https://developers.google.com/android/images)：首选的官方完整刷机包来源。
- [Google Pixel Full OTA Images](https://developers.google.com/android/ota)：官方完整 OTA 来源；首版不处理增量 OTA。
- [payload-dumper-go](https://github.com/ssut/payload-dumper-go)：解包完整 OTA 的 `payload.bin`；增量 OTA 不作为首版输入。
- [srlabs/extractor](https://github.com/srlabs/extractor)：处理 sparse、EROFS、ext4、super 和多种厂商固件容器。
- [android-simg2img](https://github.com/anestisb/android-simg2img)：转换 Android sparse image。
- [AOSP CarrierConfig](https://android.googlesource.com/platform/packages/apps/CarrierConfig/) 和 [AOSP carrier_settings](https://android.googlesource.com/platform/tools/carrier_settings/)：字段语义的上游参考。
- [GrapheneOS-Archive/carriersettings-extractor](https://github.com/GrapheneOS-Archive/carriersettings-extractor)：旧版 Pixel CarrierSettings 解析参考，项目已归档。
- [nlgntr/pixel-carriersettings-extractor](https://github.com/nlgntr/pixel-carriersettings-extractor)：较新的格式探索参考；截至本路线制定时项目较新且未声明许可证，只验证思路和格式，不复制代码或将其作为稳定依赖。

Pixel 6 及之后的多数机型采用 Tensor/Exynos-Shannon 路线，不能假设存在 Qualcomm MCFG。若要验证 Qualcomm MCFG，应另选 Pixel 5 或其他明确采用 Qualcomm 平台的官方固件，并将结果标记为独立设备范围。

### 当前完成情况

Pixel Factory Image 路线的 A1/A2 首版已经完成，入口为 `android/pixel/build_catalog.py`：

- 已用 Pixel 5 `redfin` Android 14 `UP1A.231105.001.B2` 验证官方元数据解析、下载哈希校验、sparse/ext4 解包和缓存复用。
- 已解析 1111 个 canonical CarrierSettings，其中 366 个包含相关 IMS 配置，按 PLMN/MVNO match rule 生成 819 个 profile。
- 已写入 IMS APN、LTE/NR/IWLAN、ePDG/XCAP/entitlement、能力开关、部分 SIP/REGISTER 字段、原始键和字段证据。
- 已发现并记录 117 个 Qualcomm MCFG 的路径、大小和 SHA-256；尚未语义解码 MBN 内部配置。
- 已完成 NekokoLPA2 图标打包、SQLite 完整性检查和只读封存。

下一步不是重复搭建下载流程，而是扩大规范字段映射、增加完整 OTA/新 Pixel 分区格式，并把 MCFG 语义解析做成独立可选适配器。

## 阶段二：iOS 官方 IPSW

[blacktop/ipsw](https://github.com/blacktop/ipsw) 作为 iOS 的固件获取和文件解包层：

```text
Apple 官方 IPSW/CDN
  -> blacktop/ipsw 下载、枚举和提取
  -> 本项目解析 Carrier Bundle plist/override
  -> 映射根 schema、记录字段证据
```

首版提取范围：

- IPSW URL、ProductBuildVersion、支持设备、固件版本、baseband 文件版本和哈希。
- `System/Library/Carrier Bundles/iPhone` 下的 Carrier Bundle。
- `System/Library/CountryBundles/iPhone` 下的 Country Bundle。
- `carrier.plist`、`Info.plist`、设备/版本 override 中公开的匹配、APN、IMS、VoLTE、VoWiFi、entitlement 和紧急服务静态字段。

辅助索引：

- [AppleDB](https://github.com/littlebyteorg/appledb)：设备、版本、build 和固件元数据索引。
- [ipsw.me API](https://api.ipsw.me/)：发现指向 Apple CDN 的 IPSW URL 和签名状态。
- [idevicerestore](https://github.com/libimobiledevice/idevicerestore)：Apple 恢复固件下载/恢复流程参考。
- [img4tool](https://github.com/tihmstar/img4tool)：需要处理 IMG4/IM4P 时使用，不负责 IMS 语义解析。

AppleDB 和 ipsw.me 不是 Apple 官方配置服务，只能作为索引。`source_artifacts.source_uri` 应尽量记录最终 Apple CDN 地址，并保存本地校验哈希。Apple 没有公开可直接查询运营商 IMS/VoWiFi 参数的 API。

`.bbfw` 在首版只做制品发现、设备/版本关联和哈希记录。当前没有成熟的开源项目能把 `.bbfw` 稳定转换为完整 IMS/VoWiFi profile；深度逆向不应阻塞 Carrier Bundle 提取器交付。

### 当前完成情况

I1/I2 的首个样本固定为 iPhone 16 Pro (`iPhone17,1`) iOS 26.6、build `23G71`，官方 IPSW SHA-256 为 `2dbcf24e7abd0b7d1b7e5c281bc39f9298b9959c35d0a5b6fc39b30edb0992f7`，对应 baseband 为 `Mav24-2.70.01`。iPhone 8 不作为基准，因为它不能覆盖 NR/5GC、5G SA 和 VoNR 相关配置维度。

这个选择只扩大可观察范围，不放宽证据规则。设备支持 5G/SA 不代表某一运营商 profile 一定启用 VoNR；只有 Carrier Bundle/override 中语义明确的字段才能进入 `nr_5gc`、`vonr` 或 5G SIP 配置，缺失值保持 `NULL`。

I1/I2 首版已经完成，入口为 `ios/build_catalog.py`：

- 已验证 Apple CDN/ZIP64 单成员 Range 下载、断点续传、CRC32/SHA-256 校验、AEA 解密和 APFS FUSE 导出。
- 已导出 691 个 Carrier Bundle、1901 个 bundle 符号链接和 225 个 Country Bundle，并应用 D93/D94/D47/D48 设备 override、`_Exclude` 与 MVNO override。
- 已解析 `SupportedSIMs`、PLMN/GID/ICCID 公共前缀，以及 IMS APN、LTE/NR、VoWiFi/ePDG/IKE、REGISTER Contact、entitlement 和 E911 静态配置。
- 已生成 schema v7 只读 catalog；配置统一位于 `carrier_profiles.config_json`，来源、匹配规则、图标和字段证据分别位于 v7 的 8 张物理表。
- `.bbfw` 仍只记录路径、版本、大小和哈希，不把未解码的 baseband 内容声明为 IMS 参数。

下一步是增加其他 iPhone 机型/build 的回归样本、完善已知 plist 键映射，并为具备充足磁盘和 FUSE 权限的 self-hosted runner 配置完整构建。GitHub 托管 runner 继续只运行解析器测试。

## 阶段三：Samsung 官方固件

Samsung 作为第二个 Android 厂商源，优先处理 AP 和 CSC/OMC，不以 CP/Exynos-Shannon modem 逆向作为前置条件。

优先检查：

- CSC/OMC 运营商匹配和 feature 配置。
- `epdg_apns_conf.xml` 等 ePDG/APN 配置。
- `imsservice.apk` 及其资源、数据库和配置文件。
- `product`、`vendor`、`optics`、`prism` 中的运营商覆盖。

可参考 [samfirm.js](https://github.com/jesec/samfirm.js) 获取/解包 Samsung FUS 固件，以及 [android_samsung_imsservice](https://github.com/jameskdev/android_samsung_imsservice) 定位 IMSService/ePDG 资源。APK 静态解析使用 Apktool/JADX 等工具，但入库字段必须能追溯到资源或代码键，不能把反编译推测当作确定事实。

## 阶段四：modem 适配器

Qualcomm MCFG/MBN 作为独立输入类型，而不是 Pixel/Samsung 适配器的隐式步骤。可以参考：

- [sbaresearch/mbn-mcfg-tools](https://github.com/sbaresearch/mbn-mcfg-tools)
- [Biktorgj/mcfg_tools](https://github.com/Biktorgj/mcfg_tools)
- [fenrir-naru/mbn_utils](https://github.com/fenrir-naru/mbn_utils)

这类工具依赖逆向格式，解析出的 `RegistrationConfiguration`、`ims_sip_config`、`IMSWifiDynamicConfig` 等字段必须附带原始路径、工具版本和较保守的 confidence。未知字段留在构建诊断 sidecar，确认语义后再提升到 `config_json`。

MediaTek、Exynos/Shannon 后续各自建立适配器；不能用 Qualcomm 字段模型直接套用。

## 三方 ROM 的角色

LineageOS 等三方 ROM 可以用于：

- 对比 AOSP CarrierConfig 和 APN 变化。
- 找到公开 overlay 或厂商 blob 的文件位置。
- 为解析器准备小型、可公开的测试 fixture。

三方 ROM 往往缺少原厂 IMSService、完整 ePDG 配置或 modem provisioning，也可能继承旧 vendor blob。因此其数据默认不能覆盖同设备同版本的官方固件证据，不能作为首个 catalog 的主要权威来源。

## 合并和置信度规则

1. 官方固件中直接提取的值记为 `evidence_kind='extracted'`。
2. 由 3GPP 规则生成的 ePDG/IMS 域名记为 `standard_derived`，不能冒充固件值。
3. 同一字段在不同平台或设备上冲突时保留全部 `field_evidence`，按设备/版本拆分 profile；不得静默选择“看起来正确”的值。
4. 框架能力开关不等价于网络已经开通该服务；数据库只表达来源声明。
5. 未发现的字段写 `NULL` 或不建子表记录，不用空字符串、猜测值或客户端默认值填充。
6. 只有经过字段语义验证的数据才进入 `config_json`；未识别数据不进入发布数据库。

## 交付里程碑

| 里程碑 | 可验证结果 |
|---|---|
| A1 Pixel 获取/解包 | 给定设备和 build，可重复得到已校验的镜像文件树 |
| A2 Pixel 规范化 | 至少一个 profile 可写入 schema，且每个字段有 evidence |
| I1 IPSW 获取/提取 | 给定设备和 build，可重复得到 Carrier/Country Bundles |
| I2 iOS 规范化 | plist/override 可映射为 profile，并保留 bundle 优先级 |
| S1 Samsung AP/CSC | 可定位 CSC/OMC、ePDG、IMSService 并输出原始清单 |
| M1 MCFG 探索 | 可解包样本并区分已验证字段与未知字段 |
| R1 联合发布 | iOS/Android 数据、图标、来源和证据通过 seal/test 后生成只读 SQLite |

任何里程碑都不得依赖连接真实用户设备或读取 EFS、persist、modemst、SIM/ISIM 私有内容。
