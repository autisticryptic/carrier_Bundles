# 数据库设计

## 文档状态

本文档定义并记录当前已经落地的 schema v7。根目录 `schema.sql`、`config.schema.json`、iOS/Android 导入器和测试均以 v7 为准。

v7 将旧的 29 张高度规范化表简化为 8 张表，使 SimAdmin 等消费者一次查询就能取得一份可执行的运营商静态配置，同时保留来源、哈希和字段级证据。

## 目标边界

每个 iOS 或 Android 固件独立生成一个只读 SQLite catalog。数据库只保存公开固件中的运营商静态策略、同一份固件内的客户端通用基线，以及有明确标记的 3GPP/RFC 派生值。

允许保存：

- 运营商名称、MCC/MNC 和固件公开的 GID/SPN/前缀匹配规则；
- LTE/EPC、NR/5GC、VoWiFi/ePDG 和 N3IWF 的静态接入配置；
- IMS domain/realm、IMPI/IMPU 格式模板、IMS AKA 和 SIP REGISTER 策略；
- ePDG、IKE IDi/IDr、EAP、IKE/ESP proposal、P-CSCF 发现方式；
- 运营商声明的 VoLTE、VoNR、VoWiFi、SMS over IMS、entitlement 和紧急呼叫策略；
- 固件、配置文件、解析器、原始键路径和置信度证据；
- 运营商图标 BLOB、哈希、来源和许可信息。

禁止保存：

- 完整 IMSI、ICCID、MSISDN、IMEI、IMPI 或 IMPU；
- Ki、OP/OPc、PIN、RAND、AUTN、RES、CK、IK、AUTS 或任何会话密钥；
- 网络动态下发的 P-CSCF、地址、DNS、SPI、临时端口和 AKA 结果；
- SIM/线路绑定、用户 override、注册尝试、状态、日志或统计。

运行时客户端可在内存中读取 SIM 的实际值并与静态规则比较，但不得将实际值回写到 catalog。

## 独立固件原则

每个发布数据库必须可以由单一份固件独立重建：

```text
单份官方固件
  ├── 固件通用 IMS/IWLAN 基线
  ├── 运营商配置
  ├── 经证实的设备覆盖
  └── 3GPP/RFC 标准派生
            ↓
      单独的只读 SQLite
```

允许在同一份 Pixel 固件内组合通用 IMS 基线和 CarrierSettings 运营商覆盖。禁止用 iOS 字段填充 Android profile，也禁止用 Android 字段填充 iOS profile。多固件交叉比较只用于语义验证，不用于产生互补配置。

固件 build 和制品哈希属于来源证据，但不参与运行时匹配。设备代号可保留在数据库文件名或发布 sidecar 中，不需要进入运营商数据表。不得因为配置从某台设备的固件提取，就自动生成运行时 `device_model_pattern`。只有原始配置明确将某个值限制到设备变体时，才能将它作为设备覆盖；面向通用用户态客户端的发布可排除这些覆盖。

Pixel 5 `redfin` 数据库只作为历史实验制品归档，不再进入新的默认构建、运营商 profile 或 release 合并流程。

## 八张表

### `catalog_metadata`

每个数据库只有一行，保存：

- `schema_version`、`release_id`、`generated_at`；
- `generator_name`、`generator_version`；
- `sealed`、`source_manifest_sha256`；
- 配置 JSON 契约版本。

每次构建创建新数据库，不对已发布文件就地迁移。
数据库文件自身的 SHA-256 不能存在数据库内部，否则写入哈希会再次改变文件。它由 release 附带的 `SHA256SUMS` 保存。

### `visual_assets`

保存图标的原始 PNG/SVG BLOB、media type、SHA-256、像素尺寸、上游 URL、许可和 attribution。图标在构建期打包，消费者不依赖 NekokoLPA2 或外部网络。

### `carriers`

保存稳定 `carrier_id`、显示名称、国家、TADIG、`aliases_json` 和默认图标。旧的 `carrier_aliases` 表合并为 JSON 数组，PLMN 改由匹配规则保存。

### `carrier_profiles`

每行是一份已编译的完整静态配置：

```sql
CREATE TABLE carrier_profiles (
    profile_id TEXT PRIMARY KEY,
    carrier_id TEXT NOT NULL REFERENCES carriers(carrier_id),
    display_name TEXT NOT NULL,
    profile_kind TEXT NOT NULL,
    priority INTEGER NOT NULL DEFAULT 100,
    confidence INTEGER NOT NULL,
    lte_ims_status TEXT NOT NULL,
    nr_ims_status TEXT NOT NULL,
    vowifi_status TEXT NOT NULL,
    profile_asset_id TEXT REFERENCES visual_assets(asset_id),
    config_json TEXT NOT NULL CHECK (json_valid(config_json))
);
```

三个状态字段只能为：

- `ready`：静态配置已满足客户端契约，可进入网络建立阶段；
- `partial`：存在部分配置，但缺少必需的静态策略；
- `unsupported`：来源明确禁用该服务；
- `unknown`：来源未声明能力。

`ready` 只表示静态客户端配置完整，不承诺 SIM 已开通、设备已通过运营商白名单或网络最终注册成功。

### `profile_match_rules`

用于运行时选择 profile。一行内的非空条件为 AND，同一 profile 的多行规则为 OR。仅保存：

- PLMN；
- 固件明确声明的 GID1/GID2 和 SPN；
- 固件中用于运营商/MVNO 匹配的 IMSI/ICCID 静态前缀；
- 优先级和 exclusion 规则。

不保存 `device_model_pattern`、`os_build_pattern` 或任何运行时设备代号。提取器不得将完整 IMSI/ICCID 或真机读数写入规则；过长、可能缩小到单个用户的前缀必须拒绝并报错。

### `source_artifacts`

保存官方 ROM/IPSW/配置制品的类型、URL、SHA-256、解析器版本、提取时间和许可说明。这些字段只用于审计和复现，不参与 profile 匹配；设备、OS/build/baseband 由构建摘要保存，避免把设备绑定写入运营商数据库。

### `profile_sources`

建立 profile 和来源制品的关系，并记录：

- 原始 profile key 和文件路径；
- `contribution_kind`：`firmware_default`、`carrier_policy`、`standard_default` 或 `device_override`；
- 同一固件内的覆盖优先级。

面向通用用户态客户端的 profile 默认不应包含 `device_override`。

### `field_evidence`

字段证据不再使用二十多张表的 `table_name/row_key/field_name`。`target_kind` 区分 `config`、`match_rule`、`profile` 和 `carrier`；当目标是 `config` 时，`target_path` 使用 JSON Pointer 指向 `config_json` 的最终字段：

```text
/access/vowifi/epdg/0/address
/access/vowifi/ike/identities/idi/0/value_template
/sip/common/contact_parameters/0/name
```

每条证据保存 `source_id`、`target_kind`、`target_path`、原文件路径、原始键路径、原始值 JSON、证据类型、置信度和是否被选为最终值。因此 PLMN、GID、SPN 和前缀匹配也能保留字段级来源。

证据类型为：

- `extracted`：可从官方固件定位到原始键；
- `standard_derived`：按明确的 3GPP/RFC 规则派生；
- `operator_metadata`：来自运营商公开资料。

逆向后语义未确认的原始值不进入发布数据库，只保留在提取过程的调试 sidecar 中。

## `config_json` 契约

`config_json` 使用稳定、平台无关的层次：

```json
{
  "protocol_baseline": "carrier-bundles-ims-v1",
  "ims": {
    "home_domain": "ims.mnc012.mcc502.3gppnetwork.org",
    "realm": "ims.mnc012.mcc502.3gppnetwork.org",
    "authentication": {
      "scheme": "ims_aka",
      "algorithm": "AKAv1-MD5"
    },
    "identity_templates": [
      {
        "role": "impi",
        "source": "derived_imsi",
        "value_template": "{imsi}@{home_domain}"
      }
    ]
  },
  "access": {
    "lte": {
      "apn": "ims",
      "ip_family": "ipv4v6",
      "pcscf_discovery": ["pco", "epco"]
    },
    "vowifi": {
      "epdg": [
        {
          "address": "epdg.epc.mnc012.mcc502.pub.3gppnetwork.org",
          "discovery": "static"
        }
      ],
      "pcscf_discovery": ["ike_cfg"],
      "ike": {
        "eap_method": "eap_aka",
        "initial_port": 500,
        "natt_port": 4500
      }
    }
  },
  "sip": {
    "common": {
      "register": {
        "security_agreement": "required"
      }
    }
  },
  "services": {
    "volte": true,
    "vowifi": true
  },
  "readiness": {
    "lte_missing": ["/sip/common/security_client"],
    "vowifi_missing": ["/access/vowifi/ike/identities/idi"]
  }
}
```

详细字段名、取值枚举和 JSON Schema 在实现 v7 时固定。实现不得用自由文本代替可验证枚举。

## 缺失值和继承

v7 不再使用多张子表的 `NULL` 表达继承。`config_json` 遵守以下规则：

- key 不存在：固件未提供该覆盖，消费者按 `protocol_baseline` 使用自身默认；
- `false`、`0` 或空数组：只在来源明确声明时写入，不能与缺失 key 互换；
- 禁止用空字符串表示“不覆盖”或“删除”；
- 未知字段默认不写入 JSON，也不写入无证据的猜测值；
- 明确的 SIP Header/Contact 删除使用 `action: "omit"`；
- 客户端必须先支持 `protocol_baseline` 指定的默认契约，再应用运营商覆盖。

`readiness.*_missing` 使用 JSON Pointer 列出缺少但客户端契约要求的静态配置。因此消费者不应通过检查某个可选端口是否为空来自行判定 profile 完整度。

## 匹配规则与 SIM 隐私

PLMN 是主匹配条件。GID、SPN、IMSI/ICCID 前缀只用于固件明确区分的 MVNO、子品牌或套餐变体。

```text
PLMN=50212, SPN=Maxis    -> Maxis profile
PLMN=50212, SPN=Hotlink  -> Hotlink profile
```

这些值是固件中的静态匹配规则，不是从当前用户 SIM 采集的数据。对于只需 PLMN 即能确定的主运营商，其他条件保持缺失。

## 配置解析顺序

提取器在单份固件内按以下顺序编译 profile：

```text
客户端的 protocol_baseline
  < 同份固件的 firmware_default
  < carrier_policy
  < 来源明确的 device_override
```

通用用户态 catalog 默认编译到 `carrier_policy` 为止。设备覆盖只能进入单独、明确标记的制品，不得将来源设备本身当作默认覆盖条件。

冲突时不静默覆盖：`config_json` 保存按优先级选定的值，`field_evidence` 保留所有候选值和选择结果。

## 外部读取

消费者必须以只读模式打开：

```text
file:carrier-bundles.sqlite3?mode=ro&immutable=1
```

推荐流程：

1. 使用 PLMN 查询 `profile_match_rules`；
2. 仅当规则声明 GID/SPN/前缀时，在内存中比较 SIM 实际值；
3. 按优先级选定 `profile_id`；
4. 读取 `carrier_profiles.config_json`；
5. 检查目标 access 的 readiness 状态；
6. 先加载 `protocol_baseline`，再应用 JSON 中明确存在的运营商覆盖。

一次配置查询不再需要连接 access、IMS、IKE、SIP 和多个有序子表。图标仍单独按 `asset_id` 读取，避免每次查询配置都复制大型 BLOB。

## 只读与发布

SQLite schema 无法阻止拥有文件写权限的进程修改文件。不可变性由发布流程保证：

1. 初始化工具拒绝覆盖现有数据库；
2. 提取器每次构建新文件；
3. 构建时验证 JSON Schema、匹配规则、字段证据、外键和 SQLite `quick_check`；
4. 图标打包完成后设置 `sealed=1` 并清除文件写位；
5. 消费者使用 `mode=ro&immutable=1`；
6. 发布时使用 SHA-256 和原子替换，旧 release 保持不变。

## 迁移决策

- 历史 v6 SQLite（如有）保持不变，不原地升级；
- Pixel 5 catalog 归档，不再作为新 schema 的活跃数据源；
- 新 Pixel 和后续 iPhone Pro Max 提取直接产生 v7；
- 现有 iPhone 16 Pro 解析结果作为独立 v7 对照制品；
- SimAdmin 应通过 `catalog_metadata.schema_version=7` 和 `config_contract` 选择 v7 查询路径；
- `config.schema.json`、fixture、构建验证和稳定查询示例已经随代码提供。
